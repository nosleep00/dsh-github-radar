## 1. S02 需要核实的接口 —— 结论

方案里标了【需核实】的地方，全部用「读本机已装插件的真实源码」的方式核实，结论如下。

### 1.1 右栏标签注册（原 `ctx.sidebarRightTabs.register({ id, kind, title })`）

来源：`$DSH_HOME\profiles\desktop\node_modules\dsh-better-sidebar\lib\client.js:34978-35023`
（该插件是当前 profile 里真实运行、右栏确实出东西的插件，因此它的写法就是可用的写法）。

```js
tabs.register({
  id: 'plugin:radar',        // 全局唯一；同一 id 重复注册会抛错
  kind: 'radar',
  keepMounted: true,
  priority: 'extension',
  title: () => t('radar.title'),
  guide: [{ id: 'plugin:radar', order: 100, title: () => t('radar.title'), description: ... }],
})
```

- `title` 的实际签名是 `title(address)`（官方文档 sidebar-right.md），`() => string` 同样可用，本项目用后者。
- `guide` 在文档里写的是对象，真实实现是**数组**（一个标签可以注册多个引导项）。本项目按数组写。
- 面板主体挂在 slot `sidebar.right.pane.tab`，**key 必须是标签定义的 `id`**（不是 `kind`）：

```js
ctx.slots.inject('sidebar.right.pane.tab', () =>
  ctx.slots.register(
    { name: 'sidebar.right.pane.tab', key: 'plugin:radar', locale: 'githubRadar',
      inject: (sessionId) => ({ sessionId }) },
    RadarPane,
  ),
)
```

- 服务一律用 `ctx.get('sidebarRightTabs')` 兜底取，取不到就直接返回，绝不让 `apply` 抛错。

### 1.2 会话上下文（原方案 S09 想在客户端用 `useConversation`/`useChat`）

**偏离**：客户端 hook 的形状无法离线核实（文档只列了 slot 会注入哪些 hook，没有数据结构）。改成主机端读会话事件：

- `ctx.sessions.get(sessionId)` → `{ header, snapshotEvents(): SessionEvent[] }`，
  `SessionEvent = { type, seq, time, data }`。
- 只用事件类型 `user/message`，文本在 `data.message.content[]`（`{type:'text', text}`）里。
- 参考实现：`dsh-better-sidebar\src\process-activity.ts:320-390`（反向扫描事件）。

面板展示的仍然只是「关键词 + 报错片段」，原始聊天文本不出主机进程（`signals.ts` 里截断后即丢弃）。

### 1.3 主机 ↔ 客户端通道（原方案 S08 想用 `ctx.remote.radar.*`）

**偏离**：Typert Remote 需要生成的 codegen 产物和装饰器，离线环境下风险太高。改用同源 HTTP 路由（`dsh-better-sidebar` 也是这么做的）：

- 注册：`ctx.webServer.register({ kind: 'exact', path: '/radar/state', handler })`，返回 disposer，放进 `ctx.effect`。
- 鉴权栅栏：`ctx.connection.requestRejection({ headers }) === undefined` 才放行（来源 `dsh-better-sidebar\src\index.ts:1442`），否则 403。
- 响应统一 `content-type: application/json; charset=utf-8` + `cache-control: no-store`。

已实现的接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/radar/state?sessionId=` | 当前状态；`get()` 会顺带触发后台刷新（面板轮询看到 `loading → ready`） |
| POST | `/radar/refresh` | `{ sessionId, force }`，`force` 时忽略防抖与缓存 |
| POST | `/radar/dismiss` | `{ sessionId, fullName }`，30 天内不再出现 |
| POST | `/radar/click` | `{ fullName }`，用于 owner/topic 加权（上限 +0.1） |
| GET/POST | `/radar/settings` | GET 永不回显 token（只回 `hasToken`）；POST 支持 `clearToken: true` |
| POST | `/radar/token-check` | `{ token }` → 打 `GET /rate_limit`，返回配额 |

### 1.4 AI 摘要（原方案 S18 `ctx.llm.stream`）

来源：`dsh-better-sidebar\src\index.ts:408-465`。

```js
const llm = ctx.get('llm')              // 不放进 inject：老版本可能没有这个服务
const assembler = new BlockAssembler()
for await (const chunk of llm.stream({ provider, model, messages: [createUserMessage({...})], system, maxTokens, signal })) {
  assembler.push(chunk)
}
const text = assembler.blocks().map((b) => (b.type === 'text' ? b.text : '')).join('')
```

- `provider`/`model` 解析顺序：`ctx.get('agents')?.get(sessionId)?.options` → 会话事件里最新一条 `request/header` → `ctx.get('agentDefaultModel')?.currentSelection()`。
- `@deepseek-ai/dsh-llm` 在本机 profile 的 `node_modules` 里**解析不到**（宿主用自己的加载器注入，只覆盖 profile 内的包）。实测本插件是 `link:<repo>`，`import('@deepseek-ai/dsh-llm')` 在宿主进程里失败（`ai-probe.json` 里 `module:false`）。
- 但读 `node_modules/@deepseek-ai/dsh-llm/lib/types/message.js` 发现 `createUserMessage()` 只是 `{ ...input, role: 'user', id: randomUUID() }` 再冻结，没有任何品牌类型/校验；`source.kind` 也是自由字符串（better-sidebar 用 `plugin:dsh-better-sidebar`）。因此改为**结构化自建消息**（`summarize.ts` 的 `buildUserMessage`），彻底去掉这个依赖。修完后宿主里 `ai-probe.json` = `{ready:true, llm:true}`。
- 为了让「为什么全是模板摘要」可见，`apply()` 会写两份诊断：`ai-probe.json`（L2 是否可用）、`l2.json`（上一次 L2 的 `requested/produced/route/trail`）。
- **真机结论（2026-11-13）**：`l2.json` = `{requested:5, produced:5}`，五张卡片全部升级为 `zhSource:"llm"`，`summaries.json` 落 5 条缓存。过程中排掉三个真实故障：
  1. `maxTokens: 800` 时模型回答被截断在数组中间 → 现在 `extractJsonArray` 会在 `JSON.parse` 失败后先「补 `]` 接上最后一个完整对象」，再退化为逐个 `{...}` 扫描（`scanObjects`，字符串内的花括号不计数），一行格式坏掉不再拖垮整批。
  2. 模型偶尔在字符串里带裸换行，整份 JSON 失效 → 逐对象解析时把控制字符（`\u0000-\u001f`）替换为空格，只丢坏的那一行。
  3. 同一批里重复 `fullName` 会让 `onBatch` 收到 10 行（`rows=10` 而只问了 5 条）→ `parseSummaryResponse` 现在按 `fullName` 去重（先到先得）。
  另外 `maxTokens` 提到 1200，prompt 收紧到「zh ≤30 字、why ≤12 字、最后一个字符必须是 `]`」。

### 1.5 设置写回（S19）

来源：`godot-bridge\plugin\godot-bridge.mjs:119-141`。DSH 0.2+ 走 `configEditor`：

```js
ctx.inject(['configEditor'], (cctx) => {
  const editor = cctx.configEditor
  const rows = editor.entries()
  const entry = rows.find((row) => row === ctx.fiber?.entry)
    ?? rows.find((row) => row?.options?.name === 'dsh-github-radar')
  await editor.edit(entry, (previous) => ({ ...previous, ...patch }))

```

DSH 0.1.x 的 `settings.register` 作为兜底分支保留。

### 1.6 GitHub 检索的真实现状（重要，直接影响排序）

用真实匿名请求探测（`scripts/probe-search.mjs`）：

- 匿名 `search` 配额是 **10 次/分钟**（`/rate_limit` 里的 `resources.search`），不是文档常说的 10 次/分钟「core」。
- `sort=stars` + `in:readme` 的组合**几乎没用**：`"Max retries exceeded" in:readme` 返回的是 yt-dlp、awesome-go 这类几万星的大仓库，因为它们 README 里恰好有这些词。
- 真正有效的是「把报错翻译成库类别」：`retry in:name,description,topics` 直接返回 tenacity、backoff、retry-go、Polly 这些对症的库。

据此对 S11/S12 做了两处偏离（已写进对应代码注释）：

1. `errorQueries()`：报错 → 最多两个「类别词/包名」查询（`retry`、`cors`、`encoding`…；`No module named 'x'` 直接拿 `x`）；只有识别不出类别时才退回 `"片段" in:readme`。
2. 关键词过滤：`python/pip/npm/logging/documentation` 这类「所有会话都会出现」的词降权（`GENERIC_TERMS`），只有在没有更具体词时才补位；报错本身抽出的词不再进关键词查询（由 error 查询负责）。

排序仍然是方案里的公式，只加了一条与「−penalties」一致的修正：
命中关键词 +0.06/个（上限 +0.12），一个都没命中且不是报错来源、语言也不匹配 → −0.18。

## 5. 面板「一直骨架屏」的排查与加固（15:36）

- 现场：用户打开右栏标签后只有骨架屏。宿主侧证据：`plugin-data/dsh-github-radar/routes.json` 列出六条路由全部注册成功；从终端直接 `GET /radar/state` 得到 `403 forbidden` 并写进 `requests.jsonl` → 路由与信任栅栏都正常，问题在「浏览器没有发出请求」或「请求失败但界面不反映」。
- 根因假设：旧版客户端在 `sessionId` 为空时直接 `return`，于是既不请求也不报错，`state` 恒为 `null` → 骨架屏永久停留。
- 加固（客户端）：`sessionId` 为空不再短路，改为请求 `/radar/state`（不带参数），由宿主回退到最新会话；新增 `STALL_MS = 10000` 失速检测，超时未拿到任何响应就把骨架屏换成错误块 + 重试按钮；无 `state` 且失败/失速时按 `status = 'error'` 渲染，不再出现空白面板。
- 加固（宿主）：`/radar/state`、`/radar/refresh`、`/radar/dismiss` 在缺少 `sessionId` 时回退 `newestSessionId()`（`sessions.list()` 里 `header.createdAt` 最新的一条），响应体带上真正使用的 `sessionId`。
- 诊断落盘：`route()` 包装器把每次请求追加到 `plugin-data/dsh-github-radar/requests.jsonl`（`at/method/url/status/ms/note`，>200KB 自动清空），`apply()` 落盘 `routes.json`（`webServer` 是否可用 + 已注册路由）。
- 新增 i18n：`radar.loading.stalled`（zh/en，同时写进 `client/client.js` 内联字典与 `locale/*.json`，共 51 键）。

## 6. 关键词噪声：从「Asia/zone」到「github-radar」（16:20）

面板自己打开了（`requests.jsonl` 25 条 200），但 `cache.json` 里的关键词是
`["Asia","zone","otherwise-unqualified","Browser","Interpret"]`，卡片是 react-dropzone / ZoneMinder 之类毫不相关的仓库。

**根因**：`user/message` 事件里混着 harness 注入的运行时上下文（`Current runtime context`、`Browser time zone … Asia/Shanghai`、`Approval prompts are disabled`、`<acp>` 标签、skill 目录），它们被当作「用户说的话」拿去抽关键词。

**修复（`src/host/signals.ts`）**

1. `stripHarnessNoise()`：整块删除 `<system-reminder>`/`<available_skills>`；逐行剥掉 `<acp …>` 标签（保留标签内的真实文字）；丢弃以运行时上下文句子开头的行与 skill 目录行。
2. `HARNESS_TERMS`：harness 自己的词汇（skill/approval/prompt/runtime/zone/…）一律不当关键词。
3. `MIN_MESSAGE_CHARS = 8`：跳过「好了」这类确认，窗口继续往前回溯。
4. 打分改成「按证据加权」：普通英文词 1 分、行内代码 3 分、含 `-`/`+`/`.` 的名称 +3、技术词表 +6、中文技术词映射 +6，阈值 2.5；`GENERIC_TERMS`（python/pip/logging/docs…）额外 −8，只在没别的可说时兜底。
5. 噪声形态过滤：两位非技术缩写（`md`/`in`）、版本号（`1.1.0`）、两个以上连字符（`SandianshuiLauncher-1.1.0-win-x64`）、平台后缀（`win-x64`/`linux`）、两级以上点号（`System.Text.UTF8Encoding`）、两边都带数字的短横线（`B0-10`）、发布产物后缀（`.zip/.dll/.md/…`）全部丢弃。

## 11. 空信号回退：没有线索时给「近期热门」

### 11.1 动机

用户反馈（原话）：「我希望关键词为空时，插件会推荐近期热门的项目，而不是什么都不显示」。原实现在 `isSignalEmpty` 时直接返回 `status: 'empty'`，新会话/闲聊会话里面板永远是空的。

### 11.2 查询：三条星带 + 各自的新鲜度窗口

`buildTrendingQueries()`（`src/host/query.ts`）产出三条查询，base = `Math.max(1000, minStars * 10)`：

| # | 查询 | 含义 |
|---|---|---|
| 0 | `stars:1000..2999 pushed:>=14天前` | 有真实用户的小项目 |
| 1 | `stars:3000..9999 pushed:>=10天前` | 中量级、还在维护 |
| 2 | `stars:10000..60000 pushed:>=7天前` | 大热的头部项目 |

为什么不写成一条 `stars:>=30 pushed:>=...`：GitHub 的 `sort=stars` 会把 freeCodeCamp / public-apis / build-your-own-x 这类 30–60 万星的常青清单排在最前，那不是「热门」而是「有名」。也试过 `created:>=90天` 的「新项目」路线，实测返回大量蹭热度仓库（含 `pip install public-apis` 这种荒谬安装命令），故改成「星带 + 近期有推送」。查询按天稳定，缓存 key 用 `trendingHash()` = 日期 + 查询串的哈希。

### 11.3 排序：钟形曲线 + 星带轮转

- `trendPopularity(stars)`：以 1 万星为峰值的钟形曲线（`1 - |log10(stars/10000)| / 1.6`，50 星以下为 0），替换原来的 `normStars`（后者以 20 万星为分母，导致 563k 星的老清单稳赢）。
- source 标签带上了星带序号（`trending:0/1/2`），`interleaveBySource()` 按星带轮转出卡，避免五张卡全落在同一档星数上。
- trending 模式下 `seen` 不参与过滤（固定榜单不能因为看过一次就变空），`cached.trending` 会随缓存回放带上 `trending: true`。
- 文档型仓库（awesome / list / tutorial / cheatsheet / dataset 等 topic）一律只给 `git clone`，不再猜包管理器。

### 11.4 界面

- `RadarState.trending === true` 时：提示条「会话里还没有足够的线索，先给你看最近热门的项目；点「＋ 加关键词」可以按你的方向再找」，信号区显示「近期热门」chip；卡片的 `why` 为「近期热门：关注度高、最近还在更新」。
- 新增 i18n 键 `radar.trending.chip`、`radar.trending.hint`（zh-CN / en 各一份，locale 文件各 69 键）。

### 11.5 客户端注册去重（真机故障修复）

`client-errors.jsonl` 抓到 18 条 `sidebarRight: tab type id plugin:github-radar is already registered`（每 5 秒一次）：`ctx.effect` 里做了响应式读取，服务变化会让 effect 重跑，而重跑会再次 `tabs.register()`。改为「单次注册 + 保存 disposer + cleanup 释放」：重复进入直接返回，`already registered` 视为上一个模块实例的残留并跳过，其余异常照常上报。修复后 `client-errors.jsonl` 不再增长。

### 11.7 ⟳ 换一批（用户追加需求）

用户追加（原话）：「我希望推荐近期热门的项目后，用户刷新则会换一批推荐项目」。

trending 是一个当天固定的榜单，直接 `refreshNow` 会拿到同样的五张卡。改法：

- `SessionEntry` 增 `trendShown`（本次会话已展示过的仓库）与 `trendPage`（当前搜索页）。trending 排名时把 `trendShown` 当 `seen` 传入，于是 ⟳ 取的是「下一批」而不是同一批。
- `GithubClient.search()` 增 `options.page`，URL 追加 `&page=N`，ETag 以 `query\u0000pN` 为键（否则第 2 页会命中第 1 页的校验器拿到 304）。
- 首页候选被排完（本批不足 `maxCards`）时自动翻页：清空候选与排除表，用 `page+1` 重新拉一轮，最多到 `TREND_MAX_PAGE = 5`；到顶则回到第 1 页循环。翻页属于罕见路径（一页 60 个候选 ≈ 12 次 ⟳），正常 ⟳ 不额外消耗额度。
- 文案同步：提示条改为「…点 ⟳ 换一批，或「＋ 加关键词」按你的方向找」，`radar.trending.hint` 中英文一起改。

验证（`scripts/probe-rotate.mjs`，假 GitHub 客户端 + 14 个候选，不耗匿名额度）：

⟳ #3: owner3  owner2  owner1  owner0          （只剩 4 张）
⟳ #4: owner13 owner12 owner11 owner10 owner9  （翻页到顶后回到第 1 页）
请求记录: 15 次 | p1 ×10 p2 ×3 p1 ×3
